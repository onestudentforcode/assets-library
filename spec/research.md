# 技术研究结论

## SQLite 任务队列

单机 MVP 使用 SQLite WAL。worker 在 `BEGIN IMMEDIATE` 事务内选择并抢占最早可用任务，运行期间每 30 秒更新任务心跳并周期扫描；超过两分钟没有心跳的 `running` 任务重新排队。这样既不需要 Redis，也避免 worker 异常退出后素材永久停留在“分析中”。

## 流式 multipart

Next.js Route Handler 使用 Busboy 读取 Web Stream 并直接写临时文件，检查接口对应的扩展名、声明 MIME 和大小后原子重命名并入队。内容签名、解码和视频编码校验由 worker 执行，避免大视频进入 JS 堆内存或长时间占用上传请求。

## 不转码策略

图片只接受浏览器和模型普遍可用的 JPEG、PNG、WebP。视频限定为 MP4/H.264；检测到 HEVC、VP9 或 AV1 时直接拒绝。原文件通过 Range API 预览。

## 模型兼容层

两种协议各自构造请求并统一解析为内部 Zod 模式。图片使用 data URL。视频不直接发送原文件：worker 使用 FFmpeg 生成 JPEG 关键帧并保存，再由 Chat Completions 以多图片输入分析，因此不依赖公网媒体地址。

帧数规则为 `min(5, max(1, ceil(durationSeconds)))`，时间点采用每个等分区间的中点。这样短视频约每秒一帧且避开首尾黑场，超过 5 秒的视频固定覆盖 10%、30%、50%、70%、90%。帧最长边缩放至 1280 像素并以质量 0.85 的 JPEG 编码，在覆盖范围和请求体大小之间取得平衡。

本应用使用 FFmpeg 提取视频画面，但不分析音轨。Qwen3.7 仅用于视觉理解，ASR、语言和字幕输出保持在范围外。Responses 不假设非标准多图片视频分析能力。

## 场景检测服务契约

视频分镜使用独立的 `scene-detect-service`，固定到提交 `4f29ad7141bf63c04576ecd6734578680b5968ad`。素材库使用以下同步 HTTP 契约：

- `POST /api/v1/videos/split` 上传 MP4，返回外部任务 ID、原视频时长和完整分镜清单。
- 清单中的每段包含大小、文件名和下载 URL；素材库不依赖外部任务状态轮询。
- `GET /api/v1/videos/split/{taskId}/segments/{index}` 下载单个分镜。
- `DELETE /api/v1/videos/split/{taskId}` 幂等清理原片、分镜和清单。
- `/health` 用于 Compose 健康检查。

该服务继续使用原仓库的 Python 框架、PySceneDetect 和 FFmpeg 实现，不移植到 TypeScript，也不复制进素材库主应用。当前仓库没有 Dockerfile，因此素材库部署层负责为固定 Git 提交提供包含 Python 和 FFmpeg 的运行镜像；优先通过外部容器包装完成接入，避免为部署目的改写服务源码。host 网络下绑定 `127.0.0.1:28200`，避免把无鉴权的分镜接口暴露到外部网络。

Scene Detection Service 的源码变更采用最小化原则：只有现有启动配置、公开接口契约或明确缺陷阻塞素材库集成时才允许调整；场景检测算法、分镜策略和 Python 技术栈不在本功能的重构范围内。

## 分镜大小门禁与原子批次

7 MiB 是分镜输出的固定业务门禁，使用二进制字节值 `7 × 1024 × 1024`。素材库必须先验证完整清单，只有全部元数据合格才开始下载；下载时继续按相同上限计数并复核实际文件大小，全部文件合格后才创建子素材。这样即使外部元数据与实际内容不一致，超限批次也不会触发任何模型请求或留下部分素材。

通过大小门禁后，子素材复用现有视频校验、关键帧抽取和模型分析能力。批次协调器等待所有子素材成功，再统一保持待审核或统一正式入库。任一子素材最终失败时，批次继承失败码，所有兄弟素材软删除并进入媒体清理流程。用户显式重试会破坏整批原子语义，因此失败批次只允许重新上传原视频。

批次任务必须持久化阶段并支持失联恢复。恢复逻辑以来源批次 ID 和确定性的子项标识检查既有记录与文件，重复运行只继续未完成步骤，不重复创建 Asset。外部服务不可用、超时、非法/空清单和分片下载失败统一映射为 `scene_split_failed`；清单中任一分镜超限映射为既有 `file_too_large`。
